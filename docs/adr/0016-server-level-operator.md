# A server-level Operator exists, and sees metadata only

Status: draft, 2026-10-24. Amended by [ADR-0019](0019-workspaces-share-one-sqlite-file.md): the host database is the `--db` database itself, not a separate `server.db`, so the all-workspace backup stays one file. Reverses the sentence in [ADR-0011](0011-host-workspaces-as-separate-sqlite-files.md) that there is "no Server Admin or remote control plane".

Running a paid service from SSH does not scale past the first customer: "which workspaces are suspended, which trial ends today, is last night's backup fresh?" are questions the Operator asks daily. v2 therefore adds an **Operator**: a person who is a member of no workspace, authenticates with a password and TOTP to a console at `/operator`, and can list workspaces, extend a trial, suspend and reactivate. Every action writes an operator audit line in the database. The console shows state, dates, counts, last activity and backup age, and nothing else: no entries, no notes, no names beyond what billing already needs. Support access happens through a user the customer's admin creates, which the workspace audit log records. There is no impersonation and no delete.

Why a separate identity: a workspace admin must never become the person who can suspend every workspace, and the Operator must not need an account inside a customer's database. Why metadata only: the console concentrates more authority than any other screen, so the breach radius has to be measured in fields, not intentions. Why no impersonation: support does not justify a feature that silently reads customer content, and the customer-initiated account is honest and already exists in v1. Why no console delete: deletion is the one irreversible action, and a shell command with history is a better audit than a button.

Considered and rejected: keeping the CLI (works for one customer, not for daily triage); Caddy basic auth in front of the console (one shared credential, no per-action actor, no second factor); impersonation with an audit event (still reads customer content, and becomes the highest-value target); a full control plane including billing and deletion (a second product, and money handling outside Stripe).

Consequences: a host-level SQLite file, `server.db`, was to hold operator accounts, operator audit, workspace state and the Stripe mapping; ADR-0019 puts that state in the main database instead. The all-workspace backup includes it, or a restore loses every subscription state. The Operator can still read the database file as its owner; "metadata only" is a policy and product guarantee, not encryption. Resetting the break-glass admin's credentials is the single narrow write the Operator may make inside a workspace, and it is audited there. The console is a second public surface to secure, rate limit and monitor, and on a self-hosted install it is simply absent.
