# Web Awesome supplies the UI controls

The SPA uses Web Awesome (`@awesome.me/webawesome`) for buttons, inputs, selects, textareas, checkboxes and the add-project dialog. Components are imported individually from `dist/components/*` and the default theme from `dist/styles/themes/default.css`; the app accent is mapped onto Web Awesome's brand scale in `app.css`. The four `src/lib/ui` wrappers keep their props API, so pages do not care that a custom element is underneath.

Why: these controls were hand-rolled CSS around native elements, and every new control meant more of our own focus, disabled and validation handling. Web Awesome is framework-agnostic web components, form-associated (native form submission and constraint validation keep working), themeable through CSS custom properties, and MIT licensed. It adds no second app framework in our code — we still write Svelte — but Web Awesome is built on Lit, so `lit` and `@lit/*` are in the bundle and the lockfile.

Consequences: Svelte cannot `bind:value` a custom element, so the wrappers translate `input`/`change` events back into `$bindable` props and selects take `<wa-option>` children. A custom-element host does not forward `aria-*` to the control inside its shadow root, so names and pressed state are slotted visually hidden text (or the control stays native, as the per-member role select does). The timeline, tables and nav links stay hand-written: the timeline is its own layout engine, and tables and router links need native semantics. The server CSP allows `connect-src data:` because Web Awesome's icons fetch inline SVG data URLs. A Web Awesome upgrade is now a visual regression risk, so the Playwright smoke test covers the homepage, sign in, entry, report, CSV and the admin controls: the Admin checkbox when creating a user, and a team member's role set to lead and verified over the API.
