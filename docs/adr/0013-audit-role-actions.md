# Audit role-based actions, in the mutation's transaction

An audit log records a change only when the actor's authority over the target comes from a role — an admin, or a lead acting on their team's projects — never from ownership. A user editing their own entry writes nothing. Each event stores the actor, the role used, a stable action name, the target, and the audited fields before and after as JSON; password and token hashes never enter it. The event commits in the same transaction as the mutation.

Why: the SPEC deferred the audit log as an accepted risk, and the risk it names is privilege, not timekeeping. Entry self-edits are the product working as designed; a lead archiving a project or an admin deactivating a person is someone spending authority over other people's data. That boundary also keeps the table small enough to read.

Cascades write their own events, because a change to a second row is a change to a second row: archiving a team writes one `project.archive` per archived project, and deactivating a user writes one `entry.stop` for the running entry it ends. The alternative — one event per API call — would leave "when did this project get archived?" unanswerable without searching team events.

Writes go through `Store.InTx`, which hands the handler a store bound to one transaction, so the actor stays in the handler where the principal already lives and `internal/entry` needs no actor parameter. Four store methods already open their own transaction; inside `InTx` they become savepoints, which is intended. Two of them return what they changed (`ArchiveTeam` the archived project ids, `SaveUser` the stopped entry) so the cascade events can name their targets.

Considered options: logging every write (rejected: most rows are users logging their own hours, and the log stops being readable); logging only cross-user changes (rejected: the code forbids cross-user entry edits, so the rule would match almost no events); SQLite triggers (rejected: atomic for free and sees OLD and NEW, but a trigger cannot know the actor, the capture logic moves into SQL, and `AutoMigrate` does not manage triggers); writing the event after commit (rejected: a crash between the two loses exactly the event an investigation would want); a hash chain (rejected: without an anchor held elsewhere it only proves tampering to someone who could recompute it anyway).

Consequences: the schema moves to 5, and an older binary refuses a newer database, so deploying this is a one-way door — rolling back means restoring the backup taken before the upgrade. No backfill: the log starts empty on the day it ships. It is per workspace, scoped by `workspace_id` in the shared file ([ADR-0019](0019-workspaces-share-one-sqlite-file.md)), so an operator hosting several has no single view. Events are kept forever and there is no delete path; the log resists the application, not the operator who owns the file. Reading is admin-only over `GET /audit` and `tstamps audit`; there is no web page and no MCP tool.
