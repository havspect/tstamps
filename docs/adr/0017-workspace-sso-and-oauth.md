# Per-workspace OIDC SSO, and tstamps issues the tokens agents use

Status: draft, 2026-10-24. Amends [ADR-0011](0011-host-workspaces-as-separate-sqlite-files.md) (users stay workspace-local) and supersedes v1's deferred "SSO" item in [SPEC.md](../SPEC.md).

Each workspace may trust one OIDC identity provider, configured by a workspace admin and verified by a real authorization before it is saved. Once verified, SSO is enforced: password login is refused for everyone except one **Break-glass admin** who keeps a password and TOTP. Users are created just in time from a verified `email` claim, and an existing user with that lowercased email is adopted. The IdP proves identity only; teams, roles and deactivation stay workspace decisions, and there is no SCIM or directory sync.

Each workspace is also its own OAuth 2.1 authorization server under `/w/{slug}` ([ADR-0020](0020-fosite-sqlite-oauth-server.md)): discovery, dynamic client registration, authorization code with PKCE, the device grant, rotating refresh tokens, and resource indicators so a token is valid for exactly one workspace. `POST|GET /w/{slug}/mcp` serves the existing MCP tools over Streamable HTTP, and `tstamps login` uses the device grant. The stdio MCP server is unchanged.

Why enforce rather than offer SSO beside passwords: the thing a customer buys is that a person removed at the IdP cannot sign in with an old password. A coexistence mode would leave that bypass open and make the security review a formality. Why a break-glass admin: an IdP outage or a wrong client secret must not lock a company out of its own timekeeping record, and the Operator reset is the recovery of last resort. Why tstamps issues the tokens instead of the customer's IdP: agents need a token scoped to one workspace, trial customers have no IdP, and asking every customer to register an OAuth client for agents makes adoption their problem. Why keep stdio: self-hosted installs and the published skill plugin rely on it (ADR-0012), and removing it would break them for no gain.

Considered and rejected: SAML (a second protocol, an XML signature library and its attack surface, worth adding only when a paying customer blocks on it); "Sign in with Google/Microsoft" (social login, no central deprovisioning, no custom IdP); optional SSO beside passwords (the bypass above); delegating the OAuth server to the customer's IdP (trial customers cannot, and scope-to-role mapping becomes theirs); a third-party identity vendor (less code, but identity data and per-seat cost move to someone else, a larger commitment than it looks); remote MCP only (breaks self-hosting); SCIM (a sync bug can deactivate a company).

Consequences: tstamps now runs an authorization server, the highest-value target in the product, and its tests are as important as the entry rules. A token must never cross workspaces, which makes the issuer-per-slug and the resource indicator load-bearing. The break-glass credential is a deliberate password bypass, so it needs TOTP, a single holder, and an audit event on every reset. An IdP outage means no new logins for that workspace, and support's answer is the break-glass admin, not the Operator reading data. Personal API tokens and OAuth tokens coexist and both appear under `/me/tokens`. Remote MCP adds a public, machine-driven surface that needs rate limiting and abuse handling. The published agent skill keeps working because stdio is untouched, but its documentation now has a second connection mode to mention.
