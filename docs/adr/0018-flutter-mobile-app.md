# Mobile is a Flutter app with full timeline parity and an offline outbox

Status: draft, 2026-10-24. Adds the mobile app that [SPEC.md](../SPEC.md) deferred.

The v2 phone app is Flutter, in `mobile/` of this repository, for iOS and Android. It ships the timeline and reports, and nothing else: no admin, no audit, no operator screens. The timeline keeps its interaction model in touch form: pinch to zoom day ↔ week, pan, long-press-drag to create, edge handles to retime, drag to move, tap to edit, 15-minute snap with a precision modifier. Creating an entry, starting and stopping the running entry write to a local outbox with a client-generated `client_id` and sync when the network returns; the server is the authority, so an existing running entry is adopted and an edit conflict resolves last-write-wins. `client_id` is an additive field on `POST /entries` and `POST /timer/start`, unique per user, which makes retries idempotent. Login is the workspace OAuth flow from [ADR-0017](0017-workspace-sso-and-oauth.md), not a password form.

Why Flutter: full timeline parity was the requirement, and the timeline is a custom gesture surface. Flutter gives one rendering model and one codebase for both stores with the hit-testing control that a WebView wrapper would leave to the platform. The cost is accepted knowingly: this is a second implementation of the timeline, not a port. Why full parity: the product's promise is that logging is a timeline; a stopwatch-only app would log time the product then asks the user to fix on a desktop. Why an outbox rather than online-only: the commute, the basement and the train are the reason a phone app exists, and a forgotten timer is the failure the app is for. Why server-wins: a real merge engine for time entries is a sync product of its own, and the domain allows overlaps, so the only true conflict is which running entry is real — and the server already forbids two.

Considered and rejected: Capacitor around the existing Svelte app (one UI codebase, but a WebView timeline and a real app-store review risk); React Native (a second implementation anyway, without Flutter's rendering control); two native apps (best platform feel, three UIs to keep in step); a timer-only app (does not remove the correction work); online-only (fails the commute case); offline read-only (cannot start a forgotten timer); full offline sync with merge (a sync engine that does not fit beside billing, identity and the console); push notifications and background tracking in v2 (battery, privacy policy, and a feature nobody asked for).

Consequences: the timeline now exists twice and every edge-case fix lands twice; the repository grows a third toolchain, a macOS CI runner for iOS, Apple's yearly fee and a store review that can delay a fix by days. Old installed app versions will call `/api/v1` for years, so API changes stay additive and the app must tolerate a newer server; `client_id` cannot be removed. Store listings, privacy labels and screenshots are part of the slice. Reports are adapted rather than shared, so the web and the app can disagree on layout but must agree on numbers, and a parity test checks the totals. With no push, nothing reminds a user that a timer is running; that stays a deliberate non-goal.
