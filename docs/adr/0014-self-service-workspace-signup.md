# Self-service workspace signup: verify the email, then create the workspace

A hosted server may now create workspaces from the public site: an email owner asks for a link, the link proves control of the address, and the next page picks the workspace slug, the person's name and their password. The workspace is created only when that second page is submitted. Verification gates creation rather than login, so an unverified address never writes a SQLite file, a mistyped slug costs nothing, and an abandoned signup leaves no half-workspace behind. There is still no server-wide account: the verified email exists only as a single-use pending record, and the User it becomes is workspace-local like every other (ADR-0011).

Why not create first and verify later: an unauthenticated request would create files and WAL on disk, and the "verified" state would only be a flag inside a workspace nobody has proven they may use. Why not a server-level account: it couples identities and credentials across companies, which ADR-0011 rejected, and nothing in this flow needs the email to outlive one workspace.

Email is sent through Resend's HTTP endpoint with no SDK, configured by `--email-api-key`, `--email-from` and `--public-url` (plus `--email-api-url` for a compatible endpoint). Self-service signup exists only in hosted mode and only when those are set; otherwise both the page and the API answer that signup is not enabled, which is the kill switch. Sends are limited to five per hour per IP in memory, because the only unauthenticated step is also the one that spends money and sends mail to an arbitrary address. Pending signups live as one `0600` JSON file per token under `<workspace-dir>/pending/`, named by the token's SHA-256; the directory is not a workspace and is not in the backup set, because a lost link only means asking for another. Tokens are single use and deliberately never expire: the email owner can request a fresh link whenever they want, and a TTL would add a sweeper and an error path for no security gain. A pending record that nobody clicks stays on disk until an operator removes it.

The endpoints are host-level (`POST /api/v1/signup`, `GET|POST /api/v1/signup/verify`) because they run before a workspace exists, so they are not in the per-workspace OpenAPI document; the SPA calls them with `fetch`. Both POSTs require a same-origin `Origin`, like every other browser mutation. The created admin is active, is an admin, chose their own password, and is signed in by the response, so a new workspace lands on its timeline without a second login.

Consequences: the operator still runs the box and is still the only one who can suspend or delete a workspace; signup adds no server-wide admin, no billing, no quota and no per-email cap. Email becomes a production dependency with a third-party API key and a verified sending domain. The homepage now offers "Create a workspace" on a hosted server, so the claim that operators are the only way to make a workspace is retired. Pending signups are outside backups and have no expiry; an operator who wants to cancel outstanding links deletes the `pending` directory.
