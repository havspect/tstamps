# Self-service workspace signup: verify the email, then create the workspace

Status: amended by [ADR-0019](0019-workspaces-share-one-sqlite-file.md). The flow is
unchanged; the created workspace is now a row in the shared database, not a new
SQLite file.

A hosted server may now create workspaces from the public site: an email owner asks for a link, the link proves control of the address, and the next page picks the workspace slug, the person's name and their password. The workspace is created only when that second page is submitted. Verification gates creation rather than login, so an unverified address never writes a SQLite file, a mistyped slug costs nothing, and an abandoned signup leaves no half-workspace behind. There is still no server-wide account: the verified email exists only as a single-use pending record, and the User it becomes is workspace-local like every other (ADR-0011).

Why not create first and verify later: an unauthenticated request would create files and WAL on disk, and the "verified" state would only be a flag inside a workspace nobody has proven they may use. Why not a server-level account: it couples identities and credentials across companies, which ADR-0011 rejected, and nothing in this flow needs the email to outlive one workspace.

Email is sent through Resend's HTTP endpoint with no SDK, configured by `--email-api-key`, `--email-from` and `--public-url` (plus `--email-api-url` for a compatible endpoint). Self-service signup exists only when those are set; otherwise both the page and the API answer that signup is not enabled, which is the kill switch. Sends are limited to five per hour per IP in memory, because the only unauthenticated step is also the one that spends money and sends mail to an arbitrary address. Pending signups were once one `0600` JSON file per token in a pending directory; ADR-0019 moved them to rows keyed by the token hash. Tokens are single use and deliberately never expire: the email owner can request a fresh link whenever they want, and a TTL would add a sweeper and an error path for no security gain. A pending row that nobody clicks stays until an operator removes it.

The endpoints are host-level (`POST /api/v1/signup`, `GET|POST /api/v1/signup/verify`) because they run before a workspace exists, so they are not in the per-workspace OpenAPI document; the SPA calls them with `fetch`. Both POSTs require a same-origin `Origin`, like every other browser mutation. The created admin is active, is an admin, chose their own password, and is signed in by the response, so a new workspace lands on its timeline without a second login.

Consequences: the operator still runs the box and is still the only one who can suspend or delete a workspace; signup adds no server-wide admin, no billing, no quota and no per-email cap. Email becomes a production dependency with a third-party API key and a verified sending domain. The homepage now offers "Create a workspace", so the claim that operators are the only way to make a workspace is retired. Pending signups are rows in the database ([ADR-0019](0019-workspaces-share-one-sqlite-file.md)), so a backup carries them; an abandoned row stays until an operator removes it.
